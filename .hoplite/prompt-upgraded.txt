## What the project is, and why correctness comes first

Nebula MCP is a Rust (tokio) Model Context Protocol server that gives AI agents control of a real machine: 110 tools for files, shell, processes, git, GitHub, network, Docker, browser automation, PowerShell and Windows internals. It serves stdio, and an HTTP endpoint meant to sit behind a tunnel so that its URL can be pasted into an AI platform. The repository is public (Meganugger/nebula-mcp) and describes itself as production-grade and security-gated. Its documentation says nothing is allowed by default and that "the server must never let a tool escape its configured sandbox regardless of arguments".

That promise is the product. Someone who believes the README will point a remote agent at their machine with a GitHub token in the environment. Today the promise fails in ways that are easy to trigger, so the permission model comes first and everything else is built on it.

## What is wrong

This is what was wrong with 0.1 at 66dcb54, and for the running server all of it still is: the new core answers part of it as a library, but no tool or transport uses that library yet. Count an item as fixed only when a test drives it through the real dispatcher and passes. The list is a floor from one day of auditing, not the full set, and the working log adds findings from a later pass. You are about to port every tool and the whole server, and that code is small enough to read completely, so read all of it yourself before you continue.

**The permission model does not hold.**

- The command allowlist matches the basename only (`command_key` in `crates/core/src/security.rs`; `crates/tools/src/common/exec.rs` discards the path it resolved). Reproduced: with only `echo` allowed, `terminal.run` given the path of a planted script named `echo` ran it.
- Path checks are lexical and nothing in the repository resolves symlinks. Reproduced: `fs.read` through a symlink inside an allowed root returned a file outside it. Every path-taking tool and `resources/read` share the check.
- The deny list applies only where a tool checks that exact path. Reproduced: `fs.search` returned the contents of a denied `.env`. Reported: `fs.glob` and `fs.tree` list denied names; recursive copy, move and delete never check entries; the default patterns miss `.env.local`, `id_ed25519` and case variants; setting `denied_paths` replaces the built-in list rather than extending it.
- Reproduced: allowing `/work/**` does not allow `/work` itself, so the documented example configs refuse the root directory. Read: a comment claims literal-separator globbing, but the `Glob::new` defaults let `*` cross `/`.
- Each tool is responsible for its own checks (the `Tool` trait documentation says so), and many skip them. Read: no git, Docker or PowerShell tool checks the network gate. `git.diff`, `git.log` and `git.show` push caller strings into the argument vector unvalidated, so a `from` of `--output=<path>` writes outside policy. `docker.run` places the caller's `image` positionally, so options such as a host bind mount can be injected. `terminal.run` passes a caller-supplied environment map to the child, and children inherit the server's own environment, including its auth token and any GitHub token. Reported: destructive gates are missing across git, Docker and the Windows tools; `windows.env` interpolates `scope` unescaped into PowerShell, and its elevation check is a case-sensitive string compare; `diagnostics.analyze_dump` hands caller text to `cdb -c`; `windows.service` can create a service that runs any binary as SYSTEM; `net.quic_probe` and `net.packet_capture` pass caller strings bare to curl and tcpdump.
- Read: `github.request` sends the operator's GitHub token to any URL the caller supplies. `api()` in `crates/tools/src/github.rs` uses a `path` that begins with `http` verbatim and attaches the bearer token.
- `allow_network` defaults to true (read) and cannot be scoped per tool. Reported: there is no destination policy, so loopback (including the server's own port and its unauthenticated metrics endpoint), private ranges and cloud metadata addresses are reachable, with redirects followed; `browser.*` will open `file://` URLs.
- Read: the config file hot-reloads and nothing stops the file tools from writing it. The quick start creates it in the working directory, which is the first place an operator allows.
- Read: tools advertise argument schemas, including enums and `additionalProperties: false`, but nothing validates arguments against them. Reported: several annotations are wrong, including mutating tools marked read-only.

**Processes and lifecycle.**

- Reproduced: call `terminal.run` with a shell command that backgrounds a `sleep`, pass a progress token, then cancel. The call returns `cancelled`, the grandchild keeps running, progress notifications for the dead token keep arriving every three seconds, and the server then exits on neither stdin EOF nor SIGTERM. The cause is that `ToolContext::guarded` in `crates/core/src/context.rs` drops the tool future on cancel or at the runtime ceiling before `run_raw`'s own cleanup runs, so the process-group kill and the heartbeat abort in `exec.rs` never execute. The existing cancellation test calls `run_checked` directly, which is why it passes.
- Read: even when that cleanup runs, the group gets SIGTERM and only the leader gets SIGKILL; Windows has no tree kill at all; the timeout covers `child.wait()` but not the stdin write before it or the pipe drain after it; captured output keeps only the head, though failures are usually at the tail.
- Reproduced: `net.tls_info` panics on every call, because rustls is built with both `aws-lc-rs` and `ring` and no provider is installed. The release profile sets `panic = "abort"`, so in a release build that one call would end the server for every client; in debug the request is never answered. Nothing isolates panics.
- Reported: stdio lines have no length cap; the concurrency semaphore queues without bound and a queued call cannot be cancelled; several tools and `resources/read` load whole files or bodies before applying the output cap; sessions, scheduled jobs and subscriptions have no limits or expiry, are shared by all clients, and survive a policy change.

**Protocol and transport.**

- Read: over HTTP there is one engine and one set of connection state for every client: the negotiated protocol version, the in-flight map keyed by stringified request id (two clients using id 1 collide, and either can cancel the other's call), subscriptions, sessions and jobs. `Mcp-Session-Id` is a fresh UUID on every response and is never stored or checked. Every SSE stream receives every client's notifications through one broadcast channel. POST responses never stream, so a long call cannot deliver progress on its own connection or keep a tunnelled connection alive.
- Read: HTTP auth tokens and allowed origins are a startup snapshot, so SECURITY.md's "rotate tokens by editing the config (hot-reloaded)" is untrue. Reported: the body is buffered before auth; there are no request timeouts, connection cap, failed-auth logging or rate limit; no Host check; no CORS handling, so an allow-listed browser origin still cannot connect; shutdown hangs while an SSE stream is open; the metrics endpoint has no auth and no bind guard.
- Read: `logging/setLevel` passes an arbitrary directive to the global log filter, so any client can silence the audit log; the `logging` capability is advertised but nothing emits log notifications; `resources/*` skip the category switches, concurrency limit, timeout and metrics; there is no pagination, no resource templates or completions, and no structured tool output; a tracing span guard is held across `.await` in `handle_tool_call`. Reported: batch handling differs between the two transports.
- The server tops out at MCP 2025-11-25, which is no longer the current revision (next section).

**Platforms, documentation, hygiene.**

- Resources are broken on Windows (the failing CI tests). Reported: `.cmd` shims such as `npm` cannot be spawned, and an upper-case `GIT.EXE` is denied. The 17 Windows-only tools are listed to clients on every platform and can only return `platform_unsupported` elsewhere.
- The documents disagree with the code and with each other. ARCHITECTURE says 140 tools in 16 categories. The README table and the CHANGELOG's category counts sum to 108, because diagnostics has 9 tools, not 7. The CHANGELOG says 110 tests and "MCP 2024-11-05". `config/default.toml` says there is no allow-everything switch. RUNBOOK and the built-in prompts call `fs.mkdir`, `git.add` and `git.init`, which do not exist. Reported: `git.commit` stages only tracked files, so an agent cannot commit a new file without the shell. TOOLS.md says it is generated, but nothing checks it.
- Read: unknown config keys are accepted silently, so a typo in a disable switch fails open; there are no workspace lints, dependency audit, dependabot or release workflow. Reported: the lockfile's real minimum Rust is above the declared 1.82; LICENSE-APACHE is a stub; SECURITY.md has no reporting policy.

**Worth keeping.** Empty allowlists deny and deny patterns win. Each call resolves its policy from one atomic config snapshot, and a bad config edit keeps the last good one. Commands run without a shell, with verbatim arguments. Captured output is bounded while pipes are still drained. The cancel token is registered synchronously before the next frame is read. Stdout carries only protocol and logs go to stderr. The HTTP transport refuses to start on a non-loopback address without auth and denies unknown origins by default. TLS verification has no off switch. Also keep the typed `Args` accessors, the `ToolError` categories, `fs.edit`'s exactly-once semantics, `fs.read`'s chunk protocol, the browser driver as a constant script plus a JSON config, and the dry-run `security.*` tools.

## The protocol has moved

modelcontextprotocol.io listed 2026-07-28 as the current revision when checked on 2026-11-12. What follows was read through a summarizing fetch tool, so read the pages yourself before designing anything. Start at `/specification/versioning` and `/specification/2026-07-28/changelog`.

The current revision makes the protocol stateless. The `initialize` handshake, protocol-level sessions and `Mcp-Session-Id` are gone. Each request carries its protocol version and client capabilities in `_meta`, and on HTTP also in the `MCP-Protocol-Version` header. `server/discover` is mandatory. `subscriptions/listen` replaces the GET stream and `resources/subscribe`. `ping` and `logging/setLevel` are removed. Results carry `resultType`, and list and read results carry `ttlMs` and `cacheScope`. POST requests need `Mcp-Method` and `Mcp-Name` headers. SSE resumability is removed. Several error codes changed. Roots, sampling and logging are deprecated, and tasks moved to an extension.

Revisions up to 2025-11-25 are now "legacy". The versioning page describes a dual-era server: a client that opens with `initialize` gets legacy semantics for that stdio process or HTTP session, and a request carrying modern `_meta` is served statelessly, on the same endpoint.

So 0.1 is a legacy-only implementation, and its ROADMAP plans features the current revision deletes (resumable SSE, persistent protocol sessions). Aim for a dual-era server: the current revision implemented properly, plus the legacy revisions real clients still use, with real per-session isolation on the legacy HTTP path. Nothing on the branch implements any of this yet.

## What the result should be

Judge the work by these outcomes rather than by the list above.

- Security claims are true. There is a written threat model, every guarantee in it is enforced in a place a tool author cannot skip, and each has a test that tries to break it through the real dispatcher. Anything that cannot be guaranteed is not claimed. Every reproduced item above is pinned by a regression test that failed before the fix.
- No input from a client can take the process down, and a failing tool affects only its own request.
- Cancellation, timeout, client disconnect and shutdown each leave no processes, tasks or watchers behind on all three operating systems, and shutdown finishes in bounded time.
- Two HTTP clients cannot observe or affect each other's requests, notifications, subscriptions, sessions or jobs.
- The server speaks the current MCP revision and every legacy revision it advertises, advertises no revision or capability it does not implement, and behaves differently where the revisions differ.
- Every tool validates its arguments against its schema before running. Its schema, description, annotations and structured output match what it does, its description is written for the model that will read it, and its errors tell that model how to correct the call. An agent can carry an ordinary change from an empty directory to a pushed commit with the typed tools alone.
- Linux, Windows and macOS are green in CI with format, clippy, tests, a minimum-Rust check that matches what is declared, and a dependency audit. Platform behavior is claimed only where CI exercised it.
- Every document agrees with the code, generated ones are checked for drift in CI, breaking changes have migration notes in the changelog, and the README shows how to connect real clients.
- Nothing is left at 0.1. Every crate is back in the workspace and builds, every tool that ships runs on the new core, and no code path reaches the filesystem, a process or the network except through it.

## Judgment calls

The earlier session made most of these calls and recorded them as D1 to D11 in the log: snake-case tool names, opt-in categories, directory roots, network off by default, an environment allowlist for children, the official SDK for the protocol layer, embedded OAuth next to static bearer tokens, strict config keys, version 0.2.0. They stand. Build on them without rearguing them, and overturn one only when building on it shows it to be wrong, recording why. The reasoning below is what those decisions were meant to satisfy, and it is the bar to hold the existing core to.

**Two tiers of security.** For typed tools, where the server performs the operation or builds the argument vector, the guarantee can be made real: paths confined after symlink resolution, deny patterns applied to every file a tool touches or reveals, gates enforced, destinations checked, no caller-controlled options. Arbitrary execution is different. Once `python`, `node`, `cargo`, `sh`, `git` or `docker` is allowed, or the owner's `"*"`, the child can do whatever the operating-system user can, and no argument filter changes that. The truthful statement for that tier is that it grants the agent the user's privileges, unless the operating system confines the child. Evaluate optional OS-level confinement for spawned processes (Landlock or bubblewrap on Linux, Seatbelt on macOS, Job Objects with restricted tokens or AppContainer on Windows), build what you can verify, and document exactly what is confined and what is not. Docker access is root-equivalent on most hosts and should be presented that way.

**Make the safe path the only path.** Most of the holes exist because each tool is trusted to remember its own checks, so patching them one at a time would leave the next one latent. Move enforcement to where it cannot be skipped. Examples of the property, with the design left to you: a checked-path type that only the policy can produce; one spawn function that matches the allowlist against the executable that will actually run and owns the environment and the whole process-tree lifecycle; tool metadata that declares what a tool needs and is enforced by the dispatcher; schema validation before `call`. Resolving symlinks safely for paths that do not exist yet, without a check-then-use race, is the hard part. Look at directory-handle approaches such as `openat2` with `RESOLVE_BENEATH`, or the `cap-std` crate, before settling on `canonicalize`. There is prior art worth reading first: the reference filesystem server's symlink-aware path validation, and the process sandboxes in open-source coding agents.

**Protocol layer.** The log's decision is to build on the official Rust SDK (`rmcp`) and delete the hand-written protocol crate. No server code has been written on either, so this is the one decision to confirm before you invest in it. Check that the SDK version you would use really implements the 2026-07-28 revision alongside the legacy ones, and that it leaves you enough control over transport security, per-request policy and connection state. If it does not, keeping a hand-written layer is a legitimate answer. Either way, separate connection state from the engine: per process on stdio, per real session on legacy HTTP, none for modern requests.

**Remote access.** The handoff records which clients can send a static bearer token and which need OAuth. Confirm it against the clients' current documentation, because if a static token does not work with the platforms a user would paste this URL into, the headline use case does not work. Implement what the specification's authorization section requires of a server. The log commits to an embedded single-operator authorization server; that is security-critical code, so hold it to the same standard as the permission core, with tests that attack it, and state precisely which clients are supported.

**What the owner chose.** Keep the name, the dual license, the general-purpose scope, both transports, and the `"*"` switch, which should stay but be documented and announced loudly at startup. Defaults may change where the docs already promise the safer behavior; `allow_network` defaulting to on contradicts "nothing is allowed by default".

**Breaking changes.** At 0.1.0, breaking config keys, tool names, defaults and tool arguments is acceptable when it buys safety or correctness. Record each with migration notes. Tool names have already moved from dots to underscores (D1), because several major clients reject or rewrite dots.

**Tools.** Port every category. A tool leaves the project only by a recorded decision, never because time ran out. Prefer making the existing tools correct over adding more. Add only what an agent cannot work without or what the docs already promise. Hide tools that cannot run on the current platform. Measure the size of `tools/list`, because 110 definitions is a heavy load on a client's context, and make it easy to expose only the categories in use. If a tool cannot be made safe or cannot be verified at all, say so in its description and docs or disable it by default, and record why.

**The roadmap.** ROADMAP.md is not the plan. Rewrite it at the end to say what is true.

## How to work

**Start by knowing the whole thing.** Get onto the branch and read `OVERHAUL_LOG.md` and `HANDOFF.md`. Then read the code yourself: all of the new core, then the 0.1 tools and server you are about to port. Rerun what the handoff says passes. Reading it all is what lets you do the rest without handing any of it off.

**Make the core trustworthy before building on it.** Review it against the threat model as you would someone else's pull request, since in effect it is one. Fix what you find, get clippy clean over all targets, type-check it for Windows, and get its tests green on all three operating systems in CI, starting with the macOS failures. Every later step inherits its mistakes.

**Then get one path working end to end.** Bring the server up on the new core with the `fs` category, over stdio first, so that there is a real binary again. Port the six regression tests to the new names and config and switch each one on as its fix becomes reachable. The handoff proposes porting all the tools before the server. A thin working slice first is safer, because otherwise 110 tools get written against an API that has never served a request, and from that point every commit can be tested through the real dispatcher and the real binary.

**After that, order still matters.** Do the rest of the protocol and session architecture (both eras, HTTP, client isolation, authorization), then the remaining tool categories one at a time, then platform work (process-tree kill on Windows, OS confinement where you can verify it), then dependency and CI hygiene, then the documents. Re-add each crate to the workspace as it is ported, so that every pushed commit builds and passes for what it contains. Nothing may remain excluded at the end.

**CI is your only evidence for Windows and macOS.** Every push to any branch runs it. Push often and read the logs. Locally, `cargo check --target x86_64-pc-windows-gnu` type-checks Windows code for crates without C dependencies. Do not build further on top of a red job: a failure on one platform in the core usually means a wrong assumption that the tools will then copy.

**Tests.** The 0.1 suite passed while everything above was broken, so a green suite is not evidence by itself. For each defect, write the test that fails first and drive it through the real dispatcher. Run the real binary over stdio and HTTP as well. Do not weaken, ignore or delete a test to get a pass. The six ignored regression tests are a debt, and none of them may still be ignored at the end.

**Sources.** Read the specification instead of relying on memory or on the handoff's summary of it. Several dependencies are at least one breaking release behind (for example `thiserror` 1, `axum` 0.7, `notify` 6). The handoff lists the upgrades it intended; check current versions and advisories before choosing.

**Keep the state on the branch.** Your context will turn over during this work, and the sandbox was restored from a snapshot once during the audit, so unpushed work can vanish. Commit in steps that each build and pass, push each one, and keep `OVERHAUL_LOG.md` current with the plan and status, the decisions and their reasons, and what was verified where. Keep `HANDOFF.md` accurate as well, or fold it into the log.
